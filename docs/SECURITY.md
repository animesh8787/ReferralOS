# Security model

## Authentication and sessions
- Passwords: Argon2id; policy ≥ 10 characters with a letter and a digit; login rate-limited per IP and per account; identical error for unknown user vs wrong password; "forgot password" always answers the same way. (Sign-up does answer 409 for an address that already has an account: a usability trade-off, rate-limited to 10 per hour per IP.)
- Sessions are **server-side**: the cookie holds a random token, the database holds only its SHA-256. `HttpOnly`, `SameSite=Lax`, `Secure` when `COOKIE_SECURE=true` (set it behind HTTPS). A password reset signs out every device.
- **CSRF**: double-submit token on every state-changing request (cookie + `X-CSRF-Token`, compared in constant time against the session's token). A test iterates *every* POST/PUT/PATCH/DELETE route and asserts a missing or wrong token is rejected; another iterates every route and asserts it needs a session (except the sign-in flow).
- CORS is limited to configured origins; the web app proxies `/api` so cookies are same-origin.
- Email verification and password-reset tokens are random, hashed at rest, single use and expire.

## Tenant isolation
Every user-owned table has a non-null, indexed `user_id`. Isolation is enforced **centrally**, not per endpoint: request sessions carry the user id; a SQLAlchemy hook adds `user_id = :me` to every SELECT of any user-scoped model, stamps inserts, and rejects an insert for another user. Foreign ids simply return 404.
A walker test visits **every route that takes an id** as a second user and fails if a new route is added without being covered. Shared tables hold only public reference data. Tested: ids, lists, exports, file downloads, background-task results, the shared job cache.

## Secrets and tokens
OAuth tokens and your AI key are **envelope-encrypted** (AES-GCM; a random per-record key wrapped by a key-encryption key from `APP_KEK`; production should use a KMS or secrets manager; development falls back to a local `data/.kek` file).
They are never returned by the API, never exported, never logged, and revocable (disconnect also revokes at Google). Minimum Gmail scopes: `gmail.send`; `gmail.readonly` only if you opt in to reply tracking.
No LinkedIn or Gmail passwords are ever requested.

## Input handling
- Uploads: type and size checked; content parsed defensively (corrupt, empty, image-only and wrongly-named files fail cleanly); stored under ids generated by the server (no user-controlled paths; traversal tests).
- Outbound requests: SSRF guard (no private, loopback or link-local addresses; checked after DNS and on each redirect), size and redirect limits, honest User-Agent.
- SQL: ORM with bound parameters; hostile search input is tested. Rendering: the API returns JSON and React escapes on output; CSV/Excel exports neutralise formula injection (`=`, `+`, `-`, `@`).
- Downloads are `nosniff` and attachments; file names come from a whitelist.
- Rate limits on sign-up, login, reset, uploads, exports, sending, discovery and tailoring (in-process; use a shared store before running several API instances).

## Known limitations
- Rate limiting is per process. · The development key file and the dev mailer (writes to `data/outbox/`) are not for production. · No TLS termination is provided (put a reverse proxy in front). · Account lockout is rate-based, not a persistent lock. ·
No malware scanning of uploads (they are parsed, never executed). · Security headers such as CSP and `X-Frame-Options` are not configured on the Next.js app; add them at the reverse proxy for production.

## Known limitation: DNS rebinding
The fetcher's SSRF guard resolves a hostname and rejects private/loopback/link-local addresses before connecting, but it does not pin the connection to the address it checked. A hostile DNS server could return a public address for the check and a private one for the connection. Mitigation if you expose this to untrusted users: run the API and worker in a network with no route to internal services, or pin the resolved IP in the HTTP transport.
